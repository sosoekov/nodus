# Nodus — граф связей объектов конфигурации

Внутренний сервис, в котором команда вручную документирует, как объекты учетной
системы влияют друг на друга.

Ключевая идея модели: **связь — это не ребро между двумя объектами, а механизм,
в котором участвует несколько объектов, каждый в своей роли**. Граф двудольный:
узлы-объекты и узлы-механизмы, участие объекта в механизме — ребро с ролью.

## Стек

PostgreSQL 16 · Node.js + Fastify + TypeScript (драйвер `pg`, миграции
`node-pg-migrate`) · React + Vite + Tailwind · graphology + sigma.js ·
сессионная cookie, роли viewer / editor / admin · docker-compose.

## Запуск через docker-compose

```bash
cp .env.example .env
# обязательно поменяйте SESSION_SECRET
docker compose up --build
```

Контейнер `api` сам прогоняет миграции и сид, затем поднимает сервер на
`http://localhost:3000`.

## Локальный запуск без docker

Нужен работающий PostgreSQL 16.

```bash
createdb nodus                       # или psql -c 'create database nodus'

cd server
npm install
export DATABASE_URL=postgres://nodus:nodus@localhost:5432/nodus
export SESSION_SECRET=dev-secret-change-me-to-something-long
npm run migrate:up                   # миграции
npm run seed                         # справочники, пользователи, фикстура
npm run dev                          # API на http://localhost:3000
```

В соседнем терминале:

```bash
cd web
npm install
npm run dev                          # интерфейс на http://localhost:5173
```

Vite проксирует `/api` на бэкенд, поэтому сессионная cookie работает без CORS.

Собранный фронтенд отдает сам бэкенд: если рядом лежит `web/dist`, он
доступен на том же порту, что и API. Каталог переопределяется через `WEB_DIST`.

```bash
cd web && npm run build              # после этого http://localhost:3000 отдает интерфейс
```

### Учетки после сида

Пароль берется из `SEED_PASSWORD`, по умолчанию `nodus`.

| email                | роль   |
| -------------------- | ------ |
| `admin@nodus.local`  | admin  |
| `editor@nodus.local` | editor |
| `viewer@nodus.local` | viewer |

Сид также заводит фикстуру из ТЗ — три объекта и механизм
«Определение нормы срока подбора».

## Миграции

Отдельный файл на изменение, каждая откатывается.

```bash
npm run migrate:up             # применить все
npm run migrate:down           # откатить одну
npm run migrate:down -- 10     # откатить десять
npx node-pg-migrate -m migrations create my_change -j ts   # новая миграция
```

TypeScript-миграции исполняются напрямую — Node 22 умеет снимать типы сам,
дополнительный транспайлер не нужен.

## Тесты

Покрывается только бэкенд: инварианты, версионирование, журнал изменений,
мягкое удаление.

```bash
cd server
npm test
```

Тесты работают на отдельной базе (по умолчанию `nodus_test`, переопределяется
через `TEST_DATABASE_URL`). База создается и мигрируется автоматически перед
запуском.

| Роль     | Что может                                                          |
| -------- | ------------------------------------------------------------------ |
| `viewer` | только чтение                                                      |
| `editor` | создание, правка и мягкое удаление объектов, механизмов, состава    |

## API

Все запросы требуют сессионной cookie.

### Объекты

| Метод    | Путь                                          | Роль   |
| -------- | --------------------------------------------- | ------ |
| `GET`    | `/api/objects?q=&type=&status=&subsystem=&tag=` | viewer |
| `GET`    | `/api/objects/:id` — карточка, реквизиты, механизмы по ролям | viewer |
| `GET`    | `/api/objects/similar?name=` — похожие имена   | viewer |
| `POST`   | `/api/objects`                                | editor |
| `POST`   | `/api/objects/bulk`                           | editor |
| `PATCH`  | `/api/objects/:id`                            | editor |
| `DELETE` | `/api/objects/:id?version=`                   | editor |

### Механизмы

| Метод    | Путь                                     | Роль   |
| -------- | ---------------------------------------- | ------ |
| `GET`    | `/api/mechanisms?q=&category=&status=`   | viewer |
| `GET`    | `/api/mechanisms/:id` — карточка и состав | viewer |
| `POST`   | `/api/mechanisms`                        | editor |
| `PATCH`  | `/api/mechanisms/:id`                    | editor |
| `DELETE` | `/api/mechanisms/:id?version=`           | editor |
| `PUT`    | `/api/mechanisms/:id/participants`       | editor |

### Оптимистичная блокировка

`PATCH`, `DELETE` и `PUT .../participants` требуют текущий `version` — в теле
запроса либо, для `DELETE`, в query. Если версия устарела, приходит `409`:

```json
{
  "error": "conflict",
  "message": "Объект изменен другим пользователем",
  "details": { "current": { "version": 2, "name": "Первый", "...": "..." } }
}
```

Клиенту остается показать расхождение и дать переприменить правку. Если записи
нет или она уже удалена — `404`, а не `409`.

### Синхронизация

| Метод | Путь                            | Роль   |
| ----- | ------------------------------- | ------ |
| `GET` | `/api/changes?since=&limit=`    | viewer |
| `GET` | `/api/events` — SSE             | viewer |

Клиент получает снапшот, запоминает `seq` и держит SSE-подписку. Каждый патч —
полное новое состояние сущности, поэтому применять его повторно безопасно.

```
event: hello    { "seq": 8, "user_id": "..." }        текущий курсор при подключении
id: 9
event: change   { "seq": 9, "entity_type": "object", "op": "update", "payload": {...} }
: ping                                                 раз в 25 секунд, чтобы прокси не рвали
```

При обрыве догнать можно двумя способами, оба идемпотентны:

- `GET /api/changes?since=<последний seq>` — как описано в ТЗ. Если патчей больше
  лимита, приходит `has_more: true` и запрос повторяется с новым `seq`;
- ничего не делать: `EventSource` сам переподключается и присылает
  `Last-Event-ID`, а сервер досылает пропущенное в поток.

Публикация идет строго после `COMMIT`: подписчик не может увидеть патч, которого
еще нет в базе. Откатившаяся транзакция не рассылает ничего.

Шина держится в памяти процесса — инстанс бэкенда один, Redis не нужен.

### Мягкие блокировки

| Метод    | Путь                                | Роль   |
| -------- | ----------------------------------- | ------ |
| `POST`   | `/api/locks/:entityType/:id`        | editor |
| `POST`   | `/api/locks/:entityType/:id/beat`   | editor |
| `DELETE` | `/api/locks/:entityType/:id`        | editor |

`entityType` — `object` или `mechanism`. Клиент берет блокировку при открытии
редактора и шлет heartbeat раз в 15 секунд; без heartbeat она протухает через 60
(`LOCK_TTL_SECONDS`).

Это предупреждение, а не запрет: правку через `PATCH` блокировка не отклоняет.

- захват свободной или протухшей блокировки — `200` с `lock`;
- занятая другим — `409`, в `details.lock` лежат `user_name` и `age_seconds`,
  из которых собирается баннер «Редактирует Иван, 30 сек назад»;
- «все равно редактировать» — тот же `POST` с телом `{"force": true}`;
- `beat` после перехвата отдает `409` с новым владельцем, чтобы редактор узнал,
  что блокировку увели, а не думал, что все еще держит ее;
- снять чужую блокировку через `DELETE` нельзя — вернется `released: false`.

### Что нельзя удалить

Мягкое удаление объекта отклоняется с `409`, если объект участвует хотя бы в
одном живом механизме или у него есть реквизиты; в `details` приходит список
того, что мешает. Иначе в графе оставались бы висячие ребра.

## Структура

```
server/
  migrations/        миграции node-pg-migrate, по файлу на изменение
  src/
    auth/            пароли (scrypt), сессионный плагин, роуты входа
    events/          шина патчей в памяти процесса
    repo/            работа с БД: журнал changes, объекты, механизмы, блокировки
    routes/          HTTP-роуты
    seed/            справочники, пользователи, фикстура
  tests/             тесты бэкенда (vitest)

web/
  src/
    api/             типизированный клиент и модель ответов
    auth/            вход и текущий пользователь
    components/      бейджи, markdown, баннер блокировки, выбор объекта
    hooks/           справочники, SSE-подписка, мягкая блокировка
    lib/             разбор полных имен по префиксу, шаблоны механизмов
    pages/           поиск, карточка объекта, редактор механизма, вставка
```

## Интерфейс

| Экран                 | Путь                | Что делает                                      |
| --------------------- | ------------------- | ----------------------------------------------- |
| Поиск                 | `/`                 | строка поиска, фильтры, вкладки объектов и механизмов |
| Карточка объекта      | `/objects/:id`      | описание, реквизиты, механизмы по ролям, правка  |
| Редактор механизма    | `/mechanisms/:id`   | заголовок, категория, summary, markdown с превью, состав |
| Новый механизм        | `/mechanisms/new`   | то же плюс выбор шаблона                        |
| Массовая вставка      | `/objects/bulk`     | список полных имен с разбором типов по префиксу |

### Ввод данных

- **Создание из редактора механизма.** Если в выпадающем списке участника пусто,
  кнопка «создать» появляется тут же: объект заводится заглушкой и сразу
  подставляется в строку.
- **Защита от дублей.** При вводе имени рядом показываются похожие по
  триграммам — «возможно, вы имеете в виду…». Ловит и опечатки, и латиницу,
  подмешанную в кириллицу.
- **Массовая вставка.** Тип берется из префикса до первой точки; перед
  сохранением показывается разбор, где тип можно поправить. Повторы внутри
  вставки схлопываются, уже существующие имена сервер пропускает.
- **Шаблоны механизмов.** Выбор шаблона расставляет роли участников — остается
  подставить объекты.

### Живая синхронизация

Вкладка держит одну SSE-подписку. Правка коллеги обновляет выдачу поиска и
карточку объекта сама. В редакторе механизма она не перезатирает набранное:
показывается предупреждение с кнопкой «перечитать».

Индикатор «на связи» в шапке показывает состояние подписки.

### Блокировки в интерфейсе

Открытый редактор берет мягкую блокировку и продлевает ее раз в 15 секунд.
Остальные видят баннер «Редактирует Иван, 30 сек назад», и поля у них
действительно закрыты — «все равно редактировать» переводит блокировку на себя
и открывает их. Если блокировку увели, пока вы печатали, поля остаются
открытыми: набранное уже есть, и отнимать возможность его сохранить было бы
хуже.
